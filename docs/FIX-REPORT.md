# Fix report — Community Help Platform

Date: 27 October 2026 (Asia/Calcutta). Original audited commit: `0a520905b597cbe1407530aa555dfebb3d08743c`.

## Result

The project has been restructured and the 36 audit findings have been addressed in code, documentation or explicit owner-action instructions. **34 findings have implementation/documentation changes; 2 findings retain external owner actions.** This report does not claim that live secrets have been rotated, historical public copies have disappeared or branch protection has been enabled.

The code remains the original Node.js/Express/MySQL product, with a rewritten same-origin frontend and stronger account/event workflows. Existing core database records are preserved by migrations rather than dropped.

## Structure

- `backend/src/`: application assembly, startup, configuration, authentication, validation, data access and role-specific routes.
- `backend/scripts/`: explicit migrations/admin setup and local-only mail preview.
- `database/migrations/`: original schema compatibility, hardening fields/indexes and session/notification/outbox tables.
- `frontend/`: public UI assets served by the API server.
- `tests/unit/`, `tests/integration/`, `tests/e2e/`: validation, real-MySQL workflow/race and browser/accessibility regression tests.
- `docs/`: API contract, deployment, incident response and this report.
- `.github/`: CI, dependency update policy and bug reporting.
- Root manifest/lockfile, blank environment example, ignore rules, contribution/security policy and licensing notice.

## Validation performed

Executed locally on Node.js 26.8.2 and MySQL 8.0.46 against a separate disposable database, with headless Chromium:

- Source syntax and backend module-import checks.
- ESLint and Prettier checks.
- 6 unit tests: input normalization, limits, passwords, timezone/DST rules, pagination and production configuration.
- 20 MySQL integration tests: legacy-schema migration and retry, role authorization, verification, duplicate-registration races, review versions, idempotency, capacity concurrency, organizer rejection, event edits, cutoff/count consistency, cancellation/withdrawal, reset/expiry/revocation, disabling/deletion, completion/attendance, profile resubmission and mail retry/body clearing.
- 5 browser tests: guest discovery; desktop/mobile automated accessibility; NGO creation and admin review; volunteer joining/withdrawal; expired-session cleanup; signup, verification and password recovery.
- Dependency advisory scan reports no known vulnerabilities at the time of validation. This is not a guarantee against undisclosed vulnerabilities.
- Production startup entry point and final diff checks are included in the release verification below.

The concurrent-join integration test exposed a repeatable-read snapshot issue during implementation. The transaction boundary now uses READ COMMITTED plus consistent organizer/event locks; the test confirms that a one-slot event admits exactly one of two concurrent requests.

CI is configured to repeat checks against MySQL on Node 22, 24 and 26, with browser/accessibility tests on Node 24. Local results do not imply that hosted CI has already run. Real SMTP delivery, the operator's production infrastructure and manual screen-reader usability are not independently verified by these tests. Mail queue success/retry behavior is exercised with a controlled transport stub.

## Upgrade and behavior changes

1. Back up the database, supply fresh credentials and run migrations before starting the server.
2. Run explicit admin setup to reset/enable an administrator; legacy admin accounts are disabled by the hardening migration.
3. Existing accounts must verify their email. Existing JWT tokens are intentionally invalidated by the new authentication design.
4. Events close registration at start time and use the configured IANA timezone. Editing an event or NGO profile triggers re-review; affected volunteers receive in-app notices.
5. Participant contact details are visible only to the organizer. Account deletion removes identity fields but retains historical event/audit records.
6. Production requires an HTTPS BASE_URL, an active SMTP configuration and a dedicated database user/password. The development mail preview is not a production delivery option.
7. API paths and response shapes changed; update any external API consumers using docs/API.md.
